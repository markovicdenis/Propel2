# Partial Model Projections

`ModelCriteria::project()` selects a small set of root-table columns while
still returning model objects. It is intended for read paths such as list and
GraphQL responses where loading every column would be wasteful.

Unlike `select()`, which returns scalar values or arrays, `project()` returns
explicitly partial model objects. A partial object knows exactly which columns
were loaded and refuses to treat missing data as a stored `NULL`.

## Prerequisite: regenerate models

Projection support requires models and table maps generated by this Propel
version. In particular, each generated table map contains
`HYDRATE_COLUMN_NAMES`, the ordered list of columns in a normal hydration row.

After updating Propel, regenerate every model before deploying code that calls
`project()`:

```bash
php bin/propel model:build
```

Using a projection with an old table map fails with a clear exception asking
for regeneration. This is intentional: no runtime reflection or guessing is
used to infer the generated model layout.

## Basic usage

```php
$books = BookQuery::create()
    ->filterByIsbn('9780000000001')
    ->project(['Title', 'PublishedAt'])
    ->find();

foreach ($books as $book) {
    echo $book->getTitle();
}
```

All primary-key columns are added automatically. In the example above the
loaded columns are `Id`, `Title`, and `PublishedAt`, even though only the last
two were requested.

The projection accepts normal Propel column identifiers, including PHP names:

```php
BookQuery::create()->project('Title');
BookQuery::create()->project(['Book.Title', 'Book.PublishedAt']);
```

Projection results do not enter Propel's normal instance pool. A later full
query therefore cannot accidentally reuse a partial object.

## Working with a partial object

```php
$book = BookQuery::create()->project('Title')->findOne();

$book->isPartial();                 // true
$book->getLoadedColumns();          // ['Id', 'Title']
$book->isColumnLoaded('Title');     // true
$book->isColumnLoaded('Isbn');      // false
$book->toArray();                   // contains only Id and Title
```

Accessing a scalar column that was not selected throws a `PropelException`.
This is important because an unselected column must never be mistaken for a
database `NULL`.

```php
$book->getIsbn(); // throws: Isbn was not selected for this partial model
```

If the full object is needed, reload it explicitly. Reloading replaces the
partial state with full-object state.

```php
$book->reload();
$book->getIsbn(); // now safe
```

Partial objects cannot be saved. Reload before changing and saving one:

```php
$book->setTitle('New title');
$book->save(); // throws

$book->reload();
$book->setTitle('New title');
$book->save(); // safe
```

For the same reason, `ModelCriteria::update()` rejects projected objects when
called with `forceIndividualSaves: true`. Use a normal direct update or load
full models first.

## Supported query shape

Version one supports only a flat selection from the root model table. The
following combinations are rejected:

- `join()`, `joinWith()`, `with()`, and relation hydration
- `withColumn()` and other virtual/as-columns
- select subqueries
- grouped or `HAVING` queries
- lazy-loaded columns

For example, keep a relationship query as a normal object query:

```php
// Not supported: a projection has no multi-model hydration plan.
BookQuery::create()
    ->joinWith('Book.Author')
    ->project('Title')
    ->find();

// Use normal hydration instead.
BookQuery::create()
    ->joinWith('Book.Author')
    ->find();
```

Lazy-loaded columns are deliberately excluded from projection hydration. Their
normal loading behaviour depends on a full persisted object and must remain a
separate query.

## Criteria reuse

`project()` and `select()` represent different result shapes.

- Calling `select()` after `project()` clears the projection and returns the
  normal scalar/select result.
- Calling `project()` after `select()` replaces the scalar selection with a
  partial-model projection.
- `clear()`, `count()`, and `exists()` do not leave a projection configured on
  a subsequent query.

This makes criteria clones and reused query objects safe for count and exists
paths.

## GraphQL integration

The Chipstars GraphQL model resolver uses `project()` automatically only when
all of these are true:

- the selection contains direct scalar columns of the root model only;
- no joins, grouping, subquery, custom select, or virtual columns are present;
- the resolver is not returning the model itself and does not mutate result
  objects;
- the generated table map exposes `HYDRATE_COLUMN_NAMES`.

Relations, computed GraphQL fields, and result-shaping query mutations fall
back to normal full-model hydration. This keeps the optimisation transparent to
GraphQL callers while preserving model safety.

## Performance model

Projection uses generated table-map metadata and a hydration plan cached once
per model class in the PHP process. It does not use reflection. Per row, it
maps selected values into the generated model's normal hydration order and
then delegates conversion of enums, UUIDs, dates, and database-specific types
to the normal generated `hydrate()` method.

The main benefit comes from selecting and transferring fewer database columns;
the small in-process hydration-plan lookup is negligible in comparison.
